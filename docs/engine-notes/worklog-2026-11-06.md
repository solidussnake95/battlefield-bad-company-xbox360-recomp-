1) STUTTER
----------------------------------------------------------------

1.1 The "30.5 fps" figure in the old notes was a counting bug
    bfbc_frame.cpp counted the first frame of each 2 second window in the
    rate but not in the elapsed time, so a locked 30.0 fps engine logged
    as 30.5. That wrong number is why earlier work concluded "a cap at 30
    does nothing" and removed the frame limiter.
    Fixed: the logged rate is now (frames - 1) / elapsed. The log line also
    reports the shortest and longest gap between swaps, because even spacing
    is what decides whether the picture looks smooth:
        Frame: 30.0 fps (cap 0, gap 33.2-33.4 ms)

1.2 The engine already paces itself, very evenly
    Measured 30.0 fps with 33.2-33.5 ms gaps, i.e. the jitter is around
    0.3 ms. No frame limiter is needed for the 30 fps case.

1.3 Render-target cache was far too small at 3x internal resolution
    One colour target at 3x is about 33 MB (twice that for the 16-bit HDR
    one) and the plugin shipped with a 128 MB budget for all of them, so it
    evicted and re-resolved surfaces continuously. Each eviction is a GPU
    resolve plus a clear, which is exactly a long frame.
    Changed: render target budget 128 -> 256 MB. 1024 was tried first and
    the plugin rejects it ("value 1024 exceeds max (256)"), so 256 is the
    ceiling this plugin allows.
    Also raised the general texture cache: soft 384 -> 1024 MB,
    hard 768 -> 2048 MB (verified accepted in the log).

1.4 VSync on
    30.0 fps on a 60 Hz display is exactly two refreshes per frame, so
    VSync gives a tear-free, evenly spaced picture. Note that with the host
    VSync on, presents quantise to the refresh and the frame rate cannot go
    above 30 - which matters for the 60 fps experiment in section 3.

2) DARK IMAGE / LIGHTING
----------------------------------------------------------------

2.1 Symptom
    The whole 3D world is dark while the HUD and the F5 overlay are bright:
    the scene renders as if nothing is in sunlight.

2.2 Things that were tested and RULED OUT (all measured)

    a) Shadow maps. Turned the sun shadow completely off
       (Render.ShadowsEnable false, WorldRender.ShadowmapsEnable false):
           shadows on : mean_luma 33.13 / 33.30, crushed 14.5 %
           shadows off: mean_luma 32.36,        crushed 16.0 %
       No change, so the darkness is not the shadow path.

    b) SDR instead of HDR (WorldRender.HdrEnable false):
           mean_luma 10.37, crushed 92.3 %
       Three times darker than the HDR path, so HDR/tonemapping is working
       and is not the cause. Reverted.

    c) Auto-exposure readback (d3d12_readback_resolve = "fast"): no
       brightening. Reverted to "none".

2.3 ROOT CAUSE: gamma render target conversion is inverted in this SDK
    The Xbox 360 title renders into 8_8_8_8_GAMMA surfaces. The plugin's
    UNORM16 conversion path for that format has its conversion direction
    reversed in this generation of the SDK, so every gamma-space surface
    comes out crushed. The result is a uniformly under-lit world while the
    HUD, which goes through a different path, stays bright.

    Fix: gamma_render_target_as_unorm16 = false
    The flag is init-only and the plugin registers it from its own DLL
    initialiser, which runs AFTER bfbc.toml has been read, so a value in the
    file was silently dropped before this work. It is now in the startup
    list that is pushed before GPU init, and it is also a built-in default in
    src/bfbc_app.h, so a missing config key no longer brings the darkness
    back.
    Verified in the log: "gamma_render_target_as_unorm16 = false
    (before GPU init)", including with the key removed from bfbc.toml.

2.4 Shadow range kept from the previous round
    WorldRender.ShadowmapViewDistance 300 -> 1000 m with MinScreenArea
    0.005. Outside the single 1024 px shadow map the engine treats geometry
    as shadowed, so far terrain was only ambient-lit and read as night.
    1000 m puts the map edge past the fog. Near shadows get softer as a
    result (about 1 m per texel at 1000 m). The map cannot be enlarged: the
    resolve surface is allocated 1024 wide (pitch 1040) and 2048 crashes,
    and cascades render the screen black in this title.

3) 60 / 120 FPS - WHAT IS AND IS NOT POSSIBLE
----------------------------------------------------------------

3.1 Frame rate and game speed are the same number in this port
    The engine advances one fixed simulation step per frame, so any frame
    rate above 30 runs the entire game faster by the same factor. 60 fps
    looks smooth but everything moves twice as fast.

3.2 Engine-side attempts (all measured)
    - Game.MaxFps 60 : still 30.0 fps (quantised back to the 30 Hz tick)
    - Game.MaxFps 0  : engine pacing removed, ~500 fps, unusable
    - video_mode_refresh_rate 120 : no effect on the rate
    There is no 1/30 constant in the image to patch either; the step is not
    a single float in rodata.

3.3 What does work mechanically
    Host-side pacing in bfbc_frame.cpp, driven by bfbc_pace_fps, with the
    engine cap lifted (Game.MaxFps 0):
        bfbc_pace_fps = 60  -> 60.0 fps, gaps 16.4-16.9 ms (verified)
        bfbc_pace_fps = 120 -> 120.0 fps on light scenes, falls to ~60 in
                               heavy ones at 3x internal resolution
    It is shipped as an opt-in and defaults to 0 (no pacing), because at 60
    the game runs at double speed.

4) FILES CHANGED
----------------------------------------------------------------
src/bfbc_frame.cpp
    Honest fps counter, gap logging, optional host frame pacer
    (bfbc_pace_fps).
src/bfbc_app.h
    gamma_render_target_as_unorm16 added to the pre-GPU-init push list and
    to the built-in defaults; render target and texture cache budgets raised.
tools/config_patch.py
    New profiles: shadow-bright (1000 m shadow range), shadows-off and sdr
    (diagnostics), plus the "fps" command which writes Game.MaxFps and keeps
    its value across profile changes.
tools/capture_luma.ps1, tools/capture_window_luma.ps1
    Capture the screen / the game window and report mean luminance and the
    share of crushed pixels, so renderer changes can be compared as numbers
    instead of by eye.
README.md
    Corrected the "engine runs at 30.5 fps" claim and documented that frame
    rate equals game speed.
bin\bfbc.toml (in the release package)
    gamma_render_target_as_unorm16 = false, cache budgets 256/1024/2048,
    vsync = true, bfbc_pace_fps = 0.
game\dist\xenon\config.zz (in the release package)
    Shadow range 1000 m, MinScreenArea 0.005.

5) HOW TO ROLL BACK
----------------------------------------------------------------
Darkness fix off:
    set gamma_render_target_as_unorm16 = true in bin\bfbc.toml
Shadow range back to the previous safe value:
    python tools\config_patch.py apply game\dist\xenon\config.zz shadow-safe
Whole config back to the disc original:
    python tools\config_patch.py restore game\dist\xenon\config.zz
(also: config.zz.bfbc-backup is written automatically on every apply)
60 fps opt-in:
    python tools\config_patch.py fps game\dist\xenon\config.zz 0
    then set bfbc_pace_fps = 60.000000 in bin\bfbc.toml
    (the game will run at double speed; bfbc_pace_fps = 0 undoes it)

6) STILL OPEN
----------------------------------------------------------------
- If the picture is still darker than the Xbox 360 original at the same
  spot, the next candidate is the exposure / eye-adaptation path, which was
  not proven either way: readback_resolve = "fast" did not brighten the
  scene, but that test was not run on an identical viewpoint. A screenshot
  of the same location from the original would settle it.
- A real 60 fps mod needs the per-frame simulation step patched to half
  inside the recompiled engine. That is code work with a risk to physics,
  animation timing and the mouse-aim layer, and it has not been attempted.
- The plugin refuses render target budgets above 256 MB, so 3x internal
  resolution will always be tight; 2x is the safer quality/performance point.

7) COMPLETED FIXES (2026-11-06) - MOUSE SMOOTHING TUNE
----------------------------------------------------------------
- Default bfbc_mouse_smooth reduced from 0.35 to 0.2 in src/bfbc_mouse.cpp.
  Lower EMA factor makes micro-movements more responsive while retaining
  some decay smoothing to avoid single-step per 30 Hz frame.
- Confirmed in log: MouseShape: right-stick shaping is live (gain=2 curve=1 dz=0 smooth=0.2).
- Frame timing: Frame: 30.0 fps (cap 0, gap 30.4-36.3 ms) — steady pacing.
- Key-bind normalization still active: Input: keybind_b = 'F,X,LeftCtrl' etc.

The user can adjust bfbc_mouse_smooth in bfbc.toml if 0.2 feels still too
smooth or not smooth enough; range is 0.0 (no smoothing) to 0.9 (strong smoothing).

Restart the game with the new bfbc.exe for changes to take effect.
